# **1. Introduction**

This project builds an **Autonomous Index Creation (AutoIndex)** subsystem directly into PostgreSQL’s backend.

The goal was ambitious:

> **Let PostgreSQL watch real workloads, learn which filters are slow, and automatically create the right indexes — without Admins doing manual tuning.**

Please Note : We assume liberity to draft this report as a journey rather than a dry documentation. It is written intentionally like an internal engineering development log — technical, candid, and chronological.


# **2. The Prototype — What We Started With**

Before the AutoIndex subsystem, the codebase had a **minimal prototype**:

### **2.1 SeqScan Interception**

Whenever PostgreSQL planned a sequential scan, the prototype hooked into `ExecInitSeqScan()` and extracted columns from simple `OpExpr`s:

```c
if (IsA(qual, OpExpr)) {
    Var *v = (Var *) linitial(((OpExpr*)qual)->args);
    TrackIndexCandidate(relid, &v->varattno, 1);
}
```



* Only **one column per clause**
* Only **simple `col = constant` expressions**
* Only **top-level** clauses
* No composite indexing, no boolean tree walking, no distinctness check

But the fundamental crux was present:
*“Count how often a column is used in a WHERE clause.”*

---

### **2.2 Candidate Tracking (Early Version)**

Candidates were stored in:

```c
typedef struct {
    Oid relid;
    int num_attrs;
    AttrNumber attrs[1];
    int frequency;
} IndexCandidate;
```

Problems with the above architecture

* Only **one attribute supported** (`attrs[1]`)
* Frequency increased even for tiny tables
* No locking → race conditions
* Duplicates formed easily (same attribute added repeatedly)

---

### **2.3 Background Worker**

The prototype worker woke up every 5 seconds:

```c
if (freq > 10)
    create_index();
frequency = 0;
```

This had several issues:

* **Blocking index creation** (not concurrent)
* **No check for existing indexes**
* **Frequency reset but not removed** → stale candidates remained forever
* **No scoring** aside from frequency
* No shared-memory normalization → duplicate candidates caused repeated index creation attempts

---

### **Our Observation**

| Issue                                 | Effect                                       |
| ------------------------------------- | -------------------------------------------- |
| No normalized candidate key           | `(a,b)` ≠ `(b,a)`, duplicates everywhere     |
| No shared-memory design               | backend-local state lost, inconsistent       |
| No selectivity or table size check    | indexes created on 20-row tables             |
| Index duplicates                      | PostgreSQL errors when index already existed |
| Worker executed blocking CREATE INDEX | held heavy locks                             |
| Stale candidates never removed        | shared state permanently polluted            |

---

# **3. Phase 1 — Building Shared Memory Architecture**

At this stage we realized something major:

> **Autonomous indexing cannot be done just for each process, we needed a globally active state that can coordinate for all transactions**

This changed the design direction completely.

---

## **3.1 The Shared Memory State (AutoIndexShmemState)**

We introduced a global structure:

```
┌────────────────────────────────────────────┐
│ AutoIndexShmemState                        │
│────────────────────────────────────────────│
│ global_lock                                │
│ count (number of candidates)               │
│ IndexCandidate candidates[MAX_CANDIDATES]  │
└────────────────────────────────────────────┘
```
This ensured that everyone sees the same state, 
every sequential scan contributes to it, the background worker reads from it.


### **New shared-memory layout**

```c
typedef struct {
    Oid relid;
    int num_attrs;
    AttrNumber attrs[MAX_COMPOSITE_ATTRS];
    int frequency;
    int last_frequency;
    int stale_cycles;
    int ideal_freq;
    bool freq_set;
    slock_t mutex;
} IndexCandidate;

typedef struct {
    IndexCandidate candidates[MAX_CANDIDATES];
    int count;
    slock_t global_lock;
} AutoIndexShmemState;
```


## **3.2 Composite Attribute Support**

Prototype only supported:

```c
attrs[1];   // 1 column
```

We extended:

```c
AttrNumber attrs[MAX_COMPOSITE_ATTRS];   // up to 4 columns
```

And used `qsort()` to normalize:

```c
qsort(attrs, num_attrs, sizeof(AttrNumber), compare_attrs);
```

This ensures:

```
WHERE a=… AND b=…   →  (a,b)
WHERE b=… AND a=…   →  (a,b)
```

One candidate, not two.

---

## **3.3 Preventing Duplicates**

The prototype only compared:

```
relid + single attnum
```

Now we compare full normalized composite patterns:

```c
if (cand->relid == relid &&
    cand->num_attrs == num_attrs &&
    memcmp(cand->attrs, attrs, num_attrs*sizeof(AttrNumber)) == 0)
```

This eliminated:

* accidental duplicates
* race conditions producing multiple entries
* multiple workers creating the same index

---

## **3.4 Concurrency Controls**

Shared memory required new locking rules:

* **Global SpinLock** for modifying candidate list
* **Per-candidate SpinLock** for modifying frequency

This was critical: multiple backends call `TrackIndexCandidate()` concurrently. While developing, we noticed several crashes if this was not included. 

---

## **3.5 Small Table Rejection**
We wanted the autonomous system to "fail fast", hence optimising the number of calls to CalculateIndexScore. We added conditions to reject small tables and index if it already exists as seen below. 


```c
if (rows < 1000)
    return;    // reject tiny tables
```

Because for small tables:

* SeqScan is faster
* Index adds overhead
* No benefit

This cut down noise significantly.

---

## **3.6 Early Index-Exists Check**

Before inserting a candidate:

```c
if (IndexExistsForAttrs(relid, attrs, num_attrs))
    return;
```

This solved the “duplicate index” problem observed in prototype logs.

---

# **4. Phase 2 — Heuristic-Style Scoring**

Once the candidates were normalized and stored reliably, we designed a lightweight scoring function.

## **4.1 Table Size Feature**

```c
if (rows < 1000)
    return -100;

table_size_score = log(rows);
```

Larger tables yield a higher score.

---
## **4.2 Selectivity Model**
Prototype ignored selectivity completely.

Now:

* If a column has **very few distinct values** , we penalize it.
* If **all columns** in composite are low-selective → strong penalty.
* If **at least one** is selective → composite index allowed.

This prevented pointless indexes like:

```
CREATE INDEX ON users (gender)
```

(gender has extremely low cardinality)

---
We implemented the PostgreSQL planner’s interpretation:

```c
if (stadistinct < 0)
    num_distinct = -stadistinct * rows;
else
    num_distinct = stadistinct;
selectivity = 1.0 / num_distinct;
```



| Selectivity (%) | Typical Column       | Penalty | Reason                     |
| --------------- | -------------------- | ------- | -------------------------- |
| >20%            | gender, category     | +1000   | planner won’t choose index |
| 5–20%           | semi-low cardinality | +50     | rarely used                |
| <5%             | username, email      | 0       | excellent index            |
----

## **4.3 Frequency Feature**

```c
scan_frequency_score = frequency * 10;
```

High-frequency predicates dramatically raise score.



---

## **4.3 Full Scoring Model**

Final score:

```
Score =
    + log(rows)                       (table size benefit)
    + frequency * 10                  (workload)
    - penalty                         (selectivity)
```

Threshold:

```
score > 10  → CREATE INDEX
```

This produced stable behavior.

# **5. Worker Improvements**

## **5.1 Stale Entries Flushed**

In everyday use, the Index candidate entries may accumulate and overflow. So, we removed them after 'N' cycles. We assumed N as 100 which is about 500 seconds.

```c
if (freq == last_freq)
    stale_cycles++;
if (stale_cycles >= 100)
    RemoveIndexCandidate(i);
```

---

## **5.2 Candidate Removal After Index Creation**

Initially:

```c
cand->frequency = 0;
```

But this caused confusing debugging and didnt make much sense intutively. So, we removed them. But after removal, the state table had to be updated and shuffled which led to some overhead. 


```c
RemoveIndexCandidate(i);
```


---

## **5.3 CREATE INDEX CONCURRENTLY Failed**

We noticed that just create index may be blocking and it kind of fails the reasoning behind background workers. But we were not able to implement it inside SPI. 

```sql
CREATE INDEX CONCURRENTLY ...
```

```
ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

We considered:

* committing before CIC
* running CIC via dynamic worker
* using `ProcessUtility()`

But all required larger architectural rework.

Therefore, we documented it as a known limitation and future work.

# **8. Architecture**

```
                          Query Pipeline
         ┌─────────────────────────────────────────┐
         │              Planner / Executor         │
         │        (ExecInitSeqScan Hook Points)    │
         └───────────────┬─────────────────────────┘
                         │   attributes used in WHERE
                         ▼
                 ┌──────────────────────┐
                 │ TrackIndexCandidate()│
                 └───────────┬──────────┘
                             │ writes with locks
                             ▼
            ┌──────────────────────────────────────────┐
            │     AutoIndexShmemState (Shared Memory)  │
            │ ─ candidates[]                           │
            │ ─ frequency                              │
            │ ─ last_seen (stale detection)            │
            └────────────────────┬─────────────────────┘
                                 │ periodic scan
                                 ▼
                ┌──────────────────────────────────┐
                │   AutoIndex Background Worker    │
                │ score = ML(table, stats, freq)   │
                │ if score > threshold:            │
                │     CREATE INDEX via SPI         │
                │ remove candidate                 │
                └──────────────────────────────────┘
```

# **Conclusion**

This project began with a simple prototype that reacted to every SeqScan and spawned ad-hoc workers, but we have explored and implemented it such that it has now become a better autonomous indexing subsystem. Along the way, we rebuilt candidate tracking around a shared-memory state table, fixed race conditions with normalization, and introduced a proper scoring model that uses table size, selectivity, and frequency to separate genuinely high-value indexes from noise. We ignored small tables, penalised low-distinct columns and flushed stale candidates. We have also implemented Composite index support through canonical attribute ordering, and the background worker now behaves like a real system daemon: latch-driven, safe in SPI, and responsible for cleaning up after itself. Our attempt at true concurrent index creation surfaced legitimate SPI limitations and shaped a more honest roadmap for future work. Altogether, the system now observes the workload, filters out misleading patterns, scores candidates intelligently, flushes stale entries, and creates meaningful indexes automatically.

# **Future Work**

### **Technical Enhancements**

* **Non-blocking CONCURRENT index creation**
  Explore safe mechanisms beyond SPI for launching concurrent index builds.

* **Smarter clause extraction**
  Replace simple `OpExpr` matching with a recursive clause walker that handles casts, nested AND/OR trees, functions, and planner rewrites.

* **Richer scoring model**
  Incorporate plan-cost feedback, operator selectivity, correlation statistics, or even learned weights based on historical outcomes.

* **Index lifecycle management**
  Track usage of auto-created indexes and automatically drop unused or harmful ones (“auto-vacuum for indexes”).



* **Per-table / per-database GUCs**
  Allow users to disable auto-indexing selectively or tune thresholds, scoring weights, and worker frequency.

* **Adaptive thresholds**
  Let the system dynamically adjust the score threshold based on system load, heap size, or index bloat.

* **Predictive modeling**
  Use past workload trends to predict future importance of index candidates before evidence becomes strong using basic ML models. 

* **Feedback loop from the planner**
  Learn when an index truly helped (or didn’t) by analyzing executed plans and detecting cases where created indexes remain unused and make a model learn through ot.
